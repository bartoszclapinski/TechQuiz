# Iteration 2.9 — Milestones / achievement badges

> Phase 2 · Status: in-progress

## Goal
Give the learner a sense of **progression** by surfacing **achievement badges** — milestones earned by
using the app (quizzes completed, questions answered, perfect scores, review sessions, streaks). This is
the last review/dashboard UX piece that wraps Phase 2. Badges are **derived on read** from data we
already store (quiz attempts + review sessions); there is **no new table, no migration, and no
"unlocked at" timestamp**. A badge is "unlocked" purely because the underlying count/streak has crossed
its target the moment you ask — the same derive-on-read discipline used for correctness (2.5/2.7/2.8) and
dashboard stats (2.1).

This iteration:
- adds an **`AchievementCalculator`** (pure Application logic, TDD) that turns two existing reads —
  completed quiz attempts and review-session summaries — into a fixed catalogue of badges, each with a
  **target**, a monotonic **progress** value, and an **unlocked** flag,
- exposes **`GET /api/achievements`** (`[Authorize]`, user-scoped) returning the badge list plus an
  unlocked/total roll-up,
- adds an **achievements section** to the Dashboard (unlocked badges highlighted, locked ones greyed with
  a progress hint), in both themes.

## Scope
- **In:**
  - **Application (TDD):**
    - `GetAchievementsQuery` + handler → `AchievementsDto { UnlockedCount, TotalCount,
      Items: [AchievementDto { Key, Title, Description, Group, Target, Progress, Unlocked }] }`,
      user-scoped. The handler fetches the two existing reads and delegates the math to a pure
      `AchievementCalculator` (no repo/clock deps beyond what the reads already give), so the catalogue +
      thresholds are unit-testable in isolation.
    - **Catalogue (v1, all monotonic → clean progress bars):**
      | Key | Title | Description | Target | Progress source |
      |---|---|---|---|---|
      | `first_quiz` | First Steps | Complete your first quiz | 1 | # completed attempts |
      | `ten_quizzes` | Quiz Regular | Complete 10 quizzes | 10 | # completed attempts |
      | `hundred_questions` | Centurion | Answer 100 questions | 100 | Σ attempt answers + Σ review questions |
      | `perfect_quiz` | Flawless | Score 100% on a quiz | 1 | # attempts at 100% |
      | `first_review` | First Review | Complete a daily review | 1 | # review sessions |
      | `fifty_review_correct` | Sharpshooter | Get 50 review answers right | 50 | Σ review correct |
      | `seven_day_streak` | Streak Keeper | Reach a 7-day streak | 7 | best streak over quiz+review active days |
    - `Progress = min(raw, Target)`; `Unlocked = raw >= Target`. `Group` tags each badge (`quiz` /
      `review` / `streak`) so the UI can cluster + pick an icon without hardcoding keys.
    - **Streak** reuses `StreakCalculator.LongestStreak` over the **union** of quiz + review active
      dates — an earned streak badge never un-earns when the current streak lapses (best, not current).
  - **Api:** `GET /api/achievements` (`[Authorize]`, user-scoped) → `AchievementsDto`. Thin MediatR
    wrapper; smoke tests (401 unauth, 200 with token — shape + roll-up counts).
  - **Frontend:**
    - `use-achievements` hook + `achievementsKey` query key; `fetchAchievements()` → `GET /api/achievements`.
    - **Achievements section on the Dashboard** (below existing tiles): a header ("Achievements · N/M")
      and a badge grid. Unlocked badges rendered in accent; locked badges greyed with a small
      `progress/target` hint (and a thin progress bar for multi-step badges). Both themes verified.
    - **Badge icons** — inline SVG keyed off `Group` (`quiz` / `review` / `streak`), one icon per group
      rather than a bespoke graphic per badge: less to draw, visually consistent, and the unlocked/locked
      state is carried by accent vs. greyed fill (no separate "locked" asset). Icons live under
      `web/src/features/achievements/icons/` (or an inline map). A per-badge art pass can come later.
    - **Invalidate `achievements`** wherever a quiz completes or a review is graded, so a freshly-earned
      badge appears without a manual refresh (piggyback on existing completion/grade success handlers).
- **Decisions:**
  - **(a) Derived on read, no persistence.** No `achievements` table, no `unlocked_at` column, no
    migration. A badge's state is a pure function of counts we already have. Consistent with the
    derive-on-read rule used throughout Phase 2.
  - **(b) No new repository read.** The two existing reads (`GetCompletedAttemptsWithCategoryAsync`,
    `GetReviewSessionSummariesAsync`) already carry every number the v1 catalogue needs. Adding a read
    would be premature.
  - **(c) Best streak, not current, for the streak badge.** Once you've hit 7 consecutive days the badge
    stays earned even after a lapse — a milestone is a thing you *did*, not a thing you must maintain.
  - **(d) Monotonic progress only in v1.** Every badge is a count/streak that only ever goes up, so
    `progress` is a clean fraction of `target`. Compound conditions (e.g. "90% accuracy over 20+
    questions") are deferred — they complicate the progress bar without adding much.
  - **(e) No "new badge!" notification this iteration.** A toast/highlight for *just-unlocked* badges
    needs an `unlocked_at` (to know what's new), which means persistence — deferred to a later iteration
    if it earns its keep. v1 simply shows current state.
  - **(f) Catalogue lives in the Application layer** (a static definition list the calculator walks), not
    the DB — thresholds are product decisions, versioned in code + tests, not data to be migrated.
- **Out:**
  - Any new table / migration / `unlocked_at` timestamp.
  - "New badge unlocked" notifications, toasts, or animations.
  - Compound / gated badges (accuracy-over-volume, per-category mastery) — revisit once v1 lands.
  - Achievements on the review hub or a standalone `/achievements` page — Dashboard section is enough
    for v1.
  - Sharing / social / profile badges.

## Definition of Done
- [ ] `GET /api/achievements` returns the caller's badge catalogue (key, title, description, group,
      target, progress, unlocked) plus `UnlockedCount`/`TotalCount`; `[Authorize]`, user-scoped.
- [ ] `AchievementCalculator` is pure and unit-tested: each badge's unlock boundary (just-below /
      exactly-at target), progress clamping, and the quiz+review streak union are covered.
- [ ] Handler test wires the two reads → calculator and asserts the roll-up counts.
- [ ] Dashboard shows an **Achievements** section: unlocked badges highlighted, locked ones greyed with a
      progress hint. Both themes verified.
- [ ] Completing a quiz / grading a review invalidates `achievements` so a new badge appears without a
      manual refresh.
- [ ] Full .NET suite green; `pnpm build` + lint clean.
- [ ] Manual verification in `LOG.md`: stack up, demo login → Dashboard shows achievements with correct
      unlocked/locked split → complete a quiz that crosses a threshold → badge flips to unlocked. Owner
      click-through confirms.
