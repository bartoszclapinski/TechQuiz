# Iteration 2.6 — Daily review UI

> Phase 2 · Status: done

## Goal
Surface the spaced-repetition queue (shipped API-only in 2.5) as a usable feature: a **Daily review**
card on the Dashboard ("N questions to review today") and a dedicated **review flow** that runs the
queue as a quiz-like session and, on submit, **grades** it — showing each question with the user's
answer, the correct answer, and the explanation. The `Daily review` nav item is promoted from its
`soon` state to a live route. This closes Phase 2.

## Scope (proposed — pending owner sign-off)
- **In:**
  - **Grading (backend, TDD)** — `POST /api/review/grade`: accepts the answers the user gave for a
    review session (`[{ questionId, selectedOptionId? }]`) and returns per-question results
    (`{ questionId, selectedOptionId, correctOptionId, isCorrect, explanation }`). Correctness is
    derived from the questions' options exactly like the live-quiz scoring (`Score`-style). **Stateless
    — no `QuizAttempt` persisted** (the 2.5 decision: a review spans mixed quizzes and is not an
    attempt). New repo read `GetQuestionsForGradingByIdsAsync(ids)` returns questions with options
    (incl. `IsCorrect`) + `Explanation`. `GradeReviewCommand` + handler + validator (non-empty, ≤ 50
    answers, no duplicate questionIds). Application handler/validator tests (mocked repo) + one
    Testcontainers test for the repo read; Api smoke tests (401 / 200 / 400 empty).
  - **Review flow (frontend)** — `/review` route running a **ReviewRunner** that reuses the quiz
    runner's visual shell (difficulty badge, option buttons, 1-4/Enter keyboard, progress bar). It
    fetches the queue via `GET /api/review/daily`, collects answers **locally** (no per-answer submit
    — the review isn't persisted), and on submit calls `POST /api/review/grade`. The mini-header shows
    **per-question category** (the queue is mixed-category; `ReviewQuestionDto` carries `Category`).
  - **Review summary (frontend)** — after grading, a summary screen: overall score, then each question
    with the user's pick vs. the correct option and the **explanation** (the learning payoff). Reuses
    the Result screen's visual patterns. "Done" returns to the Dashboard.
  - **Dashboard card (frontend)** — a `Daily review` card: "N questions to review today" with a CTA
    into `/review`, and a caught-up empty state ("You're all caught up — nothing to review today")
    when the queue is empty. The card and the runner share one `useDailyReview` query (React Query
    cache), so opening the review from the card needs no second fetch.
  - **Nav promotion** — remove `Daily review` from `COMING_SOON` in `app-shell`; add a live `NavLink`
    to `/review` (mirrors the History promotion in 2.4).
- **Decisions (proposed — confirm before build):**
  - **(a) Stateless grading, no `QuizAttempt`.** Continues the 2.5 decision. A review mixes questions
    from several quizzes, so it doesn't fit the single-`quizId` `QuizAttempt` model, and we don't want
    review sessions polluting History / Dashboard aggregates. Grade is a pure function of (answers,
    questions).
  - **(b) Score-at-end, not per-question reveal.** The runner collects answers and grades once on
    submit; correctness + explanations land on the **summary** screen. This reuses the existing quiz
    shell and Result patterns with one grade round-trip, versus a chattier flashcard flow (per-question
    grade calls). *Alternative on the table:* immediate per-question feedback (answer → reveal → next),
    which is the more "canonical" spaced-repetition feel but needs per-question grading and more custom
    UI. **Recommendation: ship score-at-end now**; revisit immediate-feedback as a later polish if it
    proves worth it.
  - **(c) Reuse `GET /api/review/daily` for the card count.** The Dashboard card reads the queue length
    from the same query the runner uses — no separate count endpoint. The queue is small (≤ default
    count) so fetching it for the card is cheap, and it warms the cache for the runner.
  - **(d) Hard rule #4 still holds.** `/api/review/daily` keeps omitting correctness; correctness is
    only revealed by `/api/review/grade` **after** the user submits — the same "reveal only after the
    session ends" semantics as the live quiz's Result screen. No correctness leaks during the active
    review.
- **Out:**
  - Persisting review sessions / streak credit for reviews / feeding reviews into Dashboard stats.
  - SM-2 / Leitner scheduling state (still computed on the fly from history, per 2.5).
  - A bespoke mockup-driven redesign — **no mockup exists** for the review flow or the card; we inherit
    the existing design system (quiz shell, Result screen, Dashboard tiles), as 2.4 (History) did.
  - Code-output (`QuestionType.CodeOutput`) review rendering beyond the multiple-choice shell (the
    queue is multiple-choice in the current seed; treat code-output as a later concern if it appears).
