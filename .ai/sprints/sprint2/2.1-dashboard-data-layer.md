# Iteration 2.1 — Dashboard data layer

> Phase 2 · Status: planned

## Goal
Stand up the **read-side** that the Dashboard screen (2.2) will render: one aggregate endpoint that
feeds every tile of the bento grid in a single round-trip. No UI in this iteration — just the
Application use-case, the repository aggregation, the DTO contract, and tests. 2.2 consumes it.

This is the first iteration of sprint 2 and the foundation for the whole phase: the Dashboard UI,
the time-range filter (2.3), and the History page (2.4) all build on the queries introduced here.

## What the Dashboard needs (from `mockups/dashboard-dark.html`)
The bento grid has **8 tiles**, all derivable from completed `QuizAttempt`s joined to their
`Category`:

| Tile | Data |
|---|---|
| Current streak | consecutive days ending today with ≥1 completed attempt, + a small daily-activity sparkline |
| Score over time | ordered `(completedAt, scorePercentage)` points for the line chart |
| Category strength | per-category average score (radar axes) |
| Questions answered | total answers across completed attempts |
| Average score | mean `scorePercentage` across completed attempts |
| Recent activity | last few completed attempts (category, score, date) |
| Best category | highest-average category — **derived client-side** from Category strength |
| Needs practice | lowest-average category — **derived client-side** from Category strength |

Best / Needs-practice are just the max/min of the Category-strength array, so the DTO carries the
array once and 2.2 picks the extremes — no extra fields, no double aggregation.

## Scope (decided with owner)
- **In:**
  - `GetDashboardSummaryQuery` (TDD, mocked repo) → `DashboardSummaryDto` covering all tiles.
  - One repository read that returns the user's **completed** attempts with the bits the aggregate
    needs (score, completedAt, answer count, category name), so the handler aggregates in memory.
    Integration-tested against Testcontainers PostgreSQL (ADR-008).
  - API endpoint: `GET /api/dashboard` (authenticated; scoped to the caller).
  - Empty state in the contract: no completed attempts → `averageScore: null`, empty lists,
    `currentStreakDays: 0` — so 2.2 can render the empty-state mockup off the same payload.
- **Deferred:**
  - **All UI** — bento grid, charts, sparkline → 2.2.
  - **Time-range filter** (Week/Month/All) → 2.3. 2.1 is "all time"; the query takes no range yet.
  - Read models / materialized views / caching — only if 2.x perf warrants; in-memory aggregation
    over a single user's attempts is fine at MVP volume.

## Contract (new in 2.1)
`GET /api/dashboard` → `200 DashboardSummaryDto`, `401` unauthenticated.

```
DashboardSummaryDto
  currentStreakDays:      int
  activitySparkline:      int[]            // attempt counts per day, oldest→newest (last 14 days)
  scoreOverTime:          ScorePointDto[]  // { completedAt, scorePercentage }, oldest→newest
  categoryStrength:       CategoryStrengthDto[]   // { category, averageScore, attemptCount }
  totalQuestionsAnswered: int
  averageScore:           double?          // null when no completed attempts (empty state)
  recentActivity:         RecentActivityItemDto[] // { attemptId, category, scorePercentage, completedAt }
```

Only **completed** attempts count toward aggregates (an abandoned attempt has no score). Scores are
the denormalised `QuizAttempt.ScorePercentage` (0–100), so no re-scoring of answers is needed.

## Notes
- **One endpoint, not eight** — the Dashboard renders as a unit; a single `GET /api/dashboard` is one
  round-trip and one cache key for TanStack Query, simpler than per-tile calls. The time-range filter
  (2.3) will add a query param to this same endpoint, not new routes.
- **Aggregate in memory, not in SQL (for now)** — a single user's completed attempts is a small set;
  computing streak/averages in the handler keeps the logic testable with a mocked repo and avoids
  premature read models. Revisit only if 2.x shows a perf problem (ADR-013 pragmatism).
- **Streak is date-based, server-local** — "consecutive days ending today". Decide the day boundary
  (UTC vs. user-local) when implementing the streak test; document the choice in the handler test name.
- **Owner is learning React** — no React here, but 2.2 will lean on this contract; keep the DTO field
  names aligned with the tile labels so the UI mapping in 2.2 is obvious.
