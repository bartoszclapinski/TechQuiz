# Iteration 2.5 — Spaced repetition engine

> Phase 2 · Status: planned

## Goal
A **Daily review** engine — a dedicated `GET /api/review/daily` endpoint that returns a weighted set of
questions the user should revisit: the questions they **most recently** answered incorrectly, weighted by
**difficulty** and **how long ago** they last got them wrong. This iteration ships the **API only** — no UI
(that's 2.6). The endpoint returns questions in the active-quiz `QuestionDto` shape (no correctness leaked),
ready for 2.6 to run as a quiz-like flow.

## Scope (decided with owner)
- **In:**
  - **Domain (TDD)** — pure selection logic `ReviewSelector.SelectDailyReview(candidates, count, now)`:
    one candidate per question (the user's *latest* answer for it) carrying `Difficulty`, `LastAnsweredAt`,
    `WasCorrect`. Keeps only candidates whose **latest answer was incorrect** (a question later answered
    correctly is "learned" and drops out). Weight = `difficultyFactor (Easy 1 / Medium 2 / Hard 3) +
    min(daysSinceLastWrong, 30)`. Orders by weight desc, then days desc, then `QuestionId` (stable). Takes
    `count`. Unanswered questions in a completed attempt (`SelectedOptionId == null`) count as incorrect.
  - **Application** — `GetDailyReviewQuery(int Count = 10)` + handler + validator (count 1–50). Handler:
    (1) repo `GetCompletedAnswerRowsAsync(userId)` → flat rows; (2) group by question, take latest per
    question; (3) `ReviewSelector` → chosen question IDs; (4) repo `GetQuestionsByIdsAsync(ids)` → content;
    (5) map to `ReviewQuestionDto`. Preserve the selector's order in the output.
  - **Repository** — `GetCompletedAnswerRowsAsync(userId)`: from completed+scored attempts, one row per
    answer with `{ QuestionId, Difficulty, CategoryName, AnsweredAt, WasCorrect }`. `WasCorrect` derived in
    SQL by matching `Answer.SelectedOptionId` to an `Option` with `IsCorrect = true` (null selection ⇒
    false). `GetQuestionsByIdsAsync(ids)`: questions + options for the chosen IDs. Both Testcontainers-tested.
  - **DTO** — `ReviewQuestionDto { Id, Type, Difficulty, Text, Category, Options: [{ Id, Text, OrderIndex }] }`
    — mirrors the active-quiz `QuestionDto` plus `Category` (for 2.6's mixed-category display). **No
    `IsCorrect`** on options (hard rule #4).
  - **Api** — `ReviewController` `GET /api/review/daily?count=` via MediatR, `[Authorize]`, scoped to
    `IUserContext.UserId`. Smoke tests (`WebApplicationFactory`): 401 without token, 200 with.
- **Decisions (owner-approved):**
  - **(a) Derive correctness, don't persist it.** No `IsCorrect` column added to `Answer`. Correctness is
    computed in SQL (the candidate rows) — consistent with ADR-013 pragmatism and the 2.1 in-memory
    aggregation pattern; the per-user answer set is small. Avoids a migration + backfill.
  - **(b) Latest-answer-per-question computed in C#, not EF.** Latest-per-group is awkward in EF Core; the
    repo returns raw rows and the handler/Domain reduces them — keeps the rule testable with a mocked repo.
  - **(c) Serve the `QuestionDto` shape without correctness.** 2.6 runs the review as a quiz-like flow, so
    leaking `IsCorrect` would reveal answers (hard rule #4).
- **Out:**
  - **UI / Dashboard card** ("N questions to review today") and the review *flow* + grading — that's 2.6.
    The review does **not** create a `QuizAttempt` in 2.5.
  - Cross-question scheduling state (SM-2 / Leitner boxes, due-dates). The weight is computed on the fly
    from existing answer history; no new persistent scheduling entity.

## Definition of Done
- [ ] Domain: `ReviewSelector` selects latest-wrong questions, weights by difficulty + recency, orders
      and caps to `count` — covered by pure unit tests (filtering, weighting, ordering, ties, empty).
- [ ] Application: handler (latest-per-question reduction, selector wiring, ID→content mapping, order
      preserved) and validator (count 1–50) tests with a mocked repository.
- [ ] Repository: `GetCompletedAnswerRowsAsync` (SQL-derived `WasCorrect`, completed-only, category name)
      and `GetQuestionsByIdsAsync` — Testcontainers integration tests.
- [ ] `GET /api/review/daily` returns `ReviewQuestionDto` list; `count` honored; `[Authorize]`, scoped to
      the current user; options never expose `IsCorrect`. Smoke tests green.
- [ ] Full .NET suite green.
- [ ] No EF migration / schema change (correctness derived, not stored).
- [ ] Manual verification in `LOG.md`: stack up, demo login, hit `/api/review/daily`, confirm it returns
      previously-wrong questions without correctness leaked. Owner confirms.

## Notes
- **No mockup, no UI.** Pure backend. Visible verification is a curl against the endpoint, not a browser
  click-through; the browser demo arrives in 2.6.
- **Spaced repetition, minimal form.** No SM-2/Leitner persistence — the "schedule" emerges from weighting
  existing answer history each request. If 2.6+ shows this is too thin, a scheduling entity is a later ADR.
