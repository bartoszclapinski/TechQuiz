# Iteration 4.6 — Production deployment (Azure staging)

> Phase 4 · Status: in-progress

## Goal
Take TechQuiz from "runs locally" to a **live, clickable staging URL** on Azure. The CI/CD scaffolding
already exists (`deploy-staging.yml` builds + pushes API and web to Azure App Service and applies EF
migrations), but it has **never run against real resources**, and there are concrete production gaps
between local dev and a working cross-origin deployment. This iteration provisions the Azure resources,
wires the secrets, **closes the production gaps in code/config**, and drives the **first successful
deploy** end-to-end — a reviewer can open the URL, register/login, take a quiz, and see the dashboard.

Host is **Azure** per ADR-005 (no direction change, no superseding ADR). If we later switch to a simpler
PaaS, that's a separate ADR + workflow rewrite — out of scope here.

## Split of responsibility
- **Owner (infra — outside the repo):** create the Azure resources and set the secrets (exact list in
  Tasks). I can't provision a subscription or hold secrets; these steps are yours.
- **Me (code/config/docs — in the repo):** close the production gaps, fix the deploy workflow
  inconsistency, add config knobs, document the runbook. All PR-reviewable.

## Production gaps found in the audit (what actually needs fixing)
1. **CORS is hardcoded to `http://localhost:5173`** (`Program.cs`) — production must allow the deployed
   web origin, and it must be **configuration-driven** (env var), not a code constant.
2. **Refresh cookie is `SameSite=Strict`** (`AuthController`) — API and web live on different
   `*.azurewebsites.net` subdomains, which are **cross-site** (azurewebsites.net is a public suffix), so
   the refresh cookie won't be sent. Production needs **`SameSite=None; Secure`** (Strict/Lax stays for
   local same-site dev). This is the single most likely "login works but refresh silently fails" trap.
3. **Web deploy path is inconsistent.** `web/Dockerfile` is a proper nginx image **with SPA fallback**
   (`try_files $uri /index.html`), but `deploy-staging.yml` deploys the raw `web/dist` folder to an App
   Service, which has **no SPA fallback** — a hard refresh on `/dashboard` would 404. Resolve by
   **containerizing** the web deploy (use the existing nginx image via ACR) so the fallback ships with
   it (decision (a)).
4. **Seed data is gated to `Development`** (`DataSeeder`) — a fresh staging DB would have **no demo user
   or questions**, so a reviewer can't try it without registering into an empty catalogue. Enable a
   **staging seed** (demo user + questions) so the URL is demo-ready (decision (c)).
5. **Runtime config/secrets** — connection string, JWT signing key, CORS origin, and
   `ASPNETCORE_ENVIRONMENT` must come from **App Service configuration / GitHub Secrets**, never source.
6. **Free-tier sleep** — App Service free tier sleeps after 20 min; first request is slow. Document in
   the README so reviewers aren't confused (known gotcha).

## Scope
- **In:**
  - **Config (code):**
    - CORS origin(s) read from configuration (`Cors:AllowedOrigins`), defaulting to the dev origin so
      local is unchanged; staging sets the deployed web origin.
    - Refresh cookie `SameSite` becomes environment-aware: `None` (with `Secure`) outside Development,
      `Strict` in Development. Verify the logout cookie-delete attributes match.
    - A `Staging` seed path: `DataSeeder` runs for Development **and** Staging (demo user + questions),
      still a no-op on a non-empty DB (idempotent, per the existing gotcha).
    - Confirm `/health` is suitable for the App Service health probe (it already exists).
  - **Deploy workflow (`deploy-staging.yml`):**
    - Switch the **web** job to build + push the **nginx container** (via Azure Container Registry) and
      deploy that image, so SPA fallback ships. API stays as-is (framework publish to App Service Linux),
      or is containerized too for parity — decision (b).
    - Ensure `VITE_API_BASE_URL` is baked to the real API origin at web build time (already present).
    - Keep the EF-migration step (already there), fed by `STAGING_DB_CONNECTION`.
  - **Docs:** a `docs/DEPLOYMENT.md` runbook — the exact Azure resources, the secrets, how a deploy is
    triggered (Release → deploy, or manual dispatch), and how to verify. README gets a "Live demo" link
    + the free-tier sleep note.
  - **First deploy (collaborative):** owner provisions + sets secrets; I trigger `workflow_dispatch`,
    watch it, and we verify the smoke path on the live URL.
- **Decisions:**
  - **(a) Web ships as the nginx container, not raw `dist`.** The SPA fallback already lives in the image;
    deploying static files would drop it and 404 on deep links. Reuse `web/Dockerfile` rather than add a
    parallel Azure static-fallback config.
  - **(b) API: framework publish first, containerize only if needed.** The existing workflow's
    `dotnet publish` → App Service (Linux .NET 9) is the least-moving-parts path and already written;
    containerizing the API is a follow-up only if runtime parity bites. (Web must containerize for (a);
    API needn't.)
  - **(c) Seed the staging DB** (demo user + questions) so the URL is instantly demo-able. Idempotent and
    gated to Development+Staging only — never Production-tier data assumptions.
  - **(d) Environment name is `Staging`.** Distinct from Development (which relaxes Secure cookies + Scalar
    + verbose logging) and from a future Production. Secure cookies + real CORS turn on at Staging.
  - **(e) Secrets never enter source.** Connection string, JWT key, Azure creds live in GitHub Secrets /
    App Service config. Hard rule #1.
- **Out:**
  - A separate **Production** environment / custom domain / SSL cert beyond the default
    `*.azurewebsites.net` HTTPS — staging is the deliverable; production promotion is a later step.
  - Switching host off Azure (would need a new ADR).
  - Monitoring/alerting depth (App Insights wiring beyond what exists), autoscaling, CDN.
  - Blue-green / zero-downtime deploy choreography — a single staging slot is enough.
  - Load/perf tuning (that's 4.5).

## Definition of Done
- [ ] CORS allowed origins are configuration-driven; staging allows the deployed web origin, local dev
      unchanged.
- [ ] Refresh cookie is `SameSite=None; Secure` outside Development (and still works same-site locally);
      login **and** token refresh verified on the live URL.
- [ ] Web is deployed as the nginx container with SPA fallback — a hard refresh on a deep link (e.g.
      `/dashboard`) serves the app, not a 404.
- [ ] Staging DB is seeded (demo user + questions); the live URL is demo-able without manual data entry.
- [ ] Secrets (`AZURE_CREDENTIALS`, `STAGING_DB_CONNECTION`, JWT key, CORS origin) are set outside source;
      nothing sensitive committed.
- [ ] `deploy-staging.yml` runs green end-to-end (manual dispatch) and the API `/health` is 200 on Azure.
- [ ] `docs/DEPLOYMENT.md` runbook + README "Live demo" link and free-tier sleep note.
- [ ] Smoke on the live URL: register/login → take a quiz → see result → dashboard renders. Owner confirms.
