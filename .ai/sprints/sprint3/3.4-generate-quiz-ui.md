# Iteration 3.4 — Generate screen UI (generate + preview)

> Phase 3 · Status: done

## Goal
Close the user-facing BYO-key loop: a Generate screen where the user picks topic + difficulty +
count + provider, triggers generation against `POST /api/ai/questions`, and reviews the returned
draft questions. Settings (3.3) supplied the key; this screen spends it. **Generate + preview only**
— the drafts are displayed for review but **not persisted** (the endpoint already returns drafts
without saving; persistence to the public pool is 3.5). A "Save to my pool" affordance is shown but
clearly marked as coming in 3.5, so the working effect of the key is visible now and persistence
lands separately.

## Scope (decided with owner)
- **In:** the generate form, the async generation call with progress/loading, and a read-only
  preview of the returned drafts. Provider choices come from the user's *configured* providers
  (`GET /api/ai/keys`); only Anthropic is live today.
- **Deferred to 3.5:** persisting drafts (public pool + attribution + voting). The preview's
  "Save" control is a disabled/"soon" placeholder pointing at 3.5.
- **Not in this iteration (backend boundary):** the draft DTO omits the correct-answer key
  (`CorrectOptionIndex`) by design (hard rule #4 + the 3.2 contract), so the preview shows stems,
  options, difficulty, and explanation but **not** which option is correct. Surfacing the answer to
  the draft's author is a backend/contract decision to weigh when persistence lands (3.5) — out of
  this frontend iteration.

## Contract (from `AiQuestionsController`, 3.2 — unchanged)
- `POST /api/ai/questions` `{ topic, difficulty, count, provider }` where **difficulty and provider
  cross the wire as enum *names*** ("Easy"/"Medium"/"Hard", "Anthropic") — the AI endpoints have no
  global string-enum converter (the quiz client depends on numeric `Difficulty`). This feature works
  in difficulty *names*, distinct from the numeric quiz feature.
- Returns `{ provider, questions: [{ stem, options[], difficulty, explanation? }] }`. No answer key.
- `401` unauthenticated, `409` no configured key for the provider, `400` unknown provider/difficulty.

## Notes
- **This is the first screen that calls a paid provider on the user's behalf.** Generation costs the
  user tokens, so the submit must not fire on invalid input and must clearly show it's working (no
  silent multi-second hang that invites a double-submit). Disable the button while pending.
- **Difficulty/provider as names, not ints** — the single most error-prone detail. The quiz feature
  is numeric; this feature is string. Keep the two from leaking into each other.
- **No answer key in the preview** — the draft contract omits the correct option by design. Don't
  fabricate or infer one client-side. If reviewing-without-the-answer proves too thin, that's a
  contract conversation for 3.5, recorded as an ADR — not a silent frontend workaround (hard rule #5).
- **Owner is learning React** — explain the react-hook-form/zod wiring and why generation is a
  mutation (not a query) in the PR/conversation, not in code comments.
