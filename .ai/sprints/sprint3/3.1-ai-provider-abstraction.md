# Iteration 3.1 — AI provider abstraction (TDD)

> Phase 3 · Status: done

## Goal
The Application layer can generate quiz questions through a single, provider-agnostic port. Concrete provider wiring is selectable per request, but no use case depends on a specific vendor SDK. All behavior is provable with a fake provider — no network, no real API key — keeping the iteration TDD-pure per ADR-008.

This iteration delivers the **abstraction and selection strategy**, not production-grade provider HTTP clients. A thin stub provider proves the resolver end-to-end; the real `AnthropicAiProvider` (the only vendor the owner can fund/test today) plus prompt tuning + response parsing are the bulk of iteration 3.2's infrastructure work and are integration-tested, not unit-tested.

**Provider direction (decided with owner):** ship a native `AnthropicAiProvider` first (testable now), then add **OpenRouter** as a second `IAiProvider` — one OpenAI-compatible endpoint that unlocks GPT / Gemini / open models on a single key, far better ROI than three bespoke clients. Native OpenAI/Google clients are *not* built; OpenRouter supersedes the need. OpenRouter changes ADR-006's "per-provider user keys" model, so it lands behind a **new ADR amending ADR-006** — not a silent scope change (hard rule #5).

## Definition of Done
- [x] `IAiProvider` port defined in `TechQuiz.Application/Abstractions` — generates questions from a topic/difficulty/count request, returns structured draft questions (no Domain entities crossing the boundary)
- [x] `AiProviderKind` enum (`Anthropic`, `OpenRouter`) + `IAiProviderResolver` that selects a provider implementation by kind. Unknown/unconfigured kind fails loudly, never silently falls back
- [x] `GenerateQuestionsCommand(Topic, Difficulty, Count, Provider)` + handler — validates input, resolves provider, calls abstraction once, maps drafts to DTOs. Does **not** persist (persistence is 3.5 public-pool work)
- [x] FluentValidation rules: topic non-empty, count within bounds (1–20), difficulty is a known value
- [x] DTOs: `GeneratedQuestionDraft` (stem, options, correct index, difficulty, explanation) and `GenerateQuestionsResult`
- [x] A `StubAiProvider` in Infrastructure wired in DI, registered behind the resolver, returning deterministic fake drafts — proves resolution + DI without network
- [x] `dotnet test TechQuiz.Application.Tests` green, ≥8 new tests covering: happy path per provider kind, validation failures, unknown-provider error, provider-throws propagation (18 new: 16 Application + 2 Infrastructure DI smoke)
- [x] No reference to any vendor SDK (`OpenAI`, `Anthropic.SDK`, etc.) in the Application project — those land in Infrastructure in 3.2

## Tasks (in order)
1. **Define `IAiProvider`** — `Task<IReadOnlyList<GeneratedQuestionDraft>> GenerateQuestionsAsync(GenerateQuestionsRequest, CancellationToken)`. XML doc references ADR-006. Mirror the `ICodeExecutor` port style (record request/result, `CancellationToken = default`)
2. **Draft DTOs** — `GenerateQuestionsRequest(Topic, Difficulty, Count)`, `GeneratedQuestionDraft(...)`. Keep options + correct-answer index server-side only (same discipline as `QuestionDto` omitting `IsCorrect` to the client)
3. **`AiProviderKind` enum + `IAiProviderResolver`** — `IAiProvider Resolve(AiProviderKind kind)`. Resolver throws `UnknownAiProviderException` for an unregistered kind
4. **Write failing test: provider selection** — resolver returns the registered stub for a known kind, throws for an unknown kind
5. **`GenerateQuestionsCommand` + handler (TDD)** — failing test first: valid request → resolves provider → returns mapped drafts. Then make it pass
6. **Validation (TDD)** — failing tests for empty topic, count out of range, unknown difficulty; implement `GenerateQuestionsCommandValidator`
7. **Error propagation test** — provider throws → handler surfaces a domain-meaningful error (no swallow)
8. **`StubAiProvider` in Infrastructure** — deterministic drafts; register it + the resolver in `Infrastructure/DependencyInjection.cs`
9. **DI smoke** — resolver resolves the stub via the real container (light Infrastructure test, no network)

## Notes
- **Scope guard:** this iteration is the *seam*, not the vendors. Resist implementing real HTTP clients here — the whole point (per ADR-001 Clean Architecture) is that generation logic is provable without a key or a network. Real providers + encrypted key storage are 3.2.
- **README mismatch:** `sprint3/README.md` lists OpenAI/Anthropic/Google as day-one providers; ADR-006 scopes OpenAI + Anthropic with per-provider user keys. We now diverge from both — native clients are Anthropic-only, with OpenRouter as the multi-model path. This warrants the ADR amendment noted above; the `sprint3/README.md` provider line should be refreshed once that ADR lands.
- Keys are not touched here. `GenerateQuestionsCommand` assumes a provider is resolvable; the *unconfigured* (no key) case becomes meaningful in 3.2 once key storage exists.
