# Iteration 3.2 — BYO-key storage + native Anthropic provider (first real vertical)

> Phase 3 · Status: implementation complete — pending owner live smoke (DoD line 8)

## Goal
Prove the whole bring-your-own-key vertical end-to-end with one real provider. A user stores their own Anthropic API key (encrypted at rest), and `GenerateQuestionsCommand` resolved to a real `AnthropicAiProvider` produces actual questions from Claude. This replaces the `StubAiProvider` for the Anthropic kind and is the only provider verifiable live today (the owner funds an Anthropic key); OpenAI / Gemini / OpenRouter ride the same seam in later iterations (ADR-019).

## Definition of Done
- [x] Per-user API keys stored encrypted at rest via `IDataProtectionProvider` — never logged, decrypted only at use time (ADR-006). One key per (user, provider) pair
- [x] `IAiKeyStore` abstraction (Application) + EF-backed implementation (Infrastructure): upsert / get / remove a user's key for a provider kind
- [x] Key management endpoints: add/rotate, remove, and list *which* providers the user has a key for (never returns the key material itself)
- [x] `AnthropicAiProvider` (Infrastructure) implementing `IAiProvider` for `AiProviderKind.Anthropic` — calls the Messages API, parses a structured question set, maps to `GeneratedQuestionDraft`. Registered in place of `StubAiProvider` for the Anthropic kind
- [x] Provider pulls the *current user's* decrypted Anthropic key at request time; a missing key surfaces a clear, typed error (`MissingAiKeyException` → 409, not a 500)
- [x] `AiProviderKind` extended to `{ Anthropic, OpenAi, Gemini, OpenRouter }` (the latter two unimplemented — resolver throws `UnknownAiProviderException` until their iterations)
- [x] Application tests green for key-store use cases + handler behavior with a missing key (mocked); Infrastructure integration tests for the EF key store (Testcontainers) and the Anthropic provider against mocked HTTP
- [ ] **Live smoke (owner's manual step):** with the owner's real key configured, `POST /api/ai/questions` returns Claude-authored drafts. Cannot be automated — needs a funded Anthropic key. Steps: `dotnet user-secrets set "Ai:Anthropic:..."` is *not* needed (key is per-user); instead `PUT /api/ai/keys {"provider":"Anthropic","apiKey":"sk-ant-..."}` as the demo user, then `POST /api/ai/questions {"topic":"C# records","difficulty":"Easy","count":3,"provider":"Anthropic"}` and confirm real drafts come back + grep logs for absence of the key
- [x] No key material in logs, in DTOs, or serialized to the client (verified by a test asserting the list endpoint omits the key)

## Tasks (in order)
1. **`AiProviderKind` += OpenAi, Gemini** — extend the enum (values only; no implementations yet). Resolver already throws for unregistered kinds
2. **`IAiKeyStore` abstraction (TDD-shaped)** — `Task UpsertAsync(userId, kind, plaintextKey)`, `Task<string?> GetAsync(userId, kind)`, `Task RemoveAsync(userId, kind)`, `Task<IReadOnlyList<AiProviderKind>> ListConfiguredAsync(userId)`. Application-layer port
3. **Key management use cases** — `SetAiKeyCommand`, `RemoveAiKeyCommand`, `GetConfiguredProvidersQuery` + handlers + validators. TDD against a mocked `IAiKeyStore`. List/Get never expose key material
4. **EF key entity + encryption** — `UserAiKey` (UserId, Kind, EncryptedKey, timestamps); store encrypts with `IDataProtectionProvider` on write, decrypts on read. Migration. Unique index on (UserId, Kind)
5. **EF key store integration test** — round-trip via Testcontainers: upsert → get returns plaintext, raw column is ciphertext, remove works, upsert twice rotates
6. **`AnthropicAiProvider`** — typed `HttpClient`, calls Messages API with a generation prompt, parses a strict JSON question schema → `GeneratedQuestionDraft`. Pulls the current user's key via `IAiKeyStore` + `IUserContext`; missing key → `MissingAiKeyException`
7. **Provider HTTP test** — against a mocked handler: valid response parses to drafts; malformed/empty response surfaces a typed parse error; missing key short-circuits before any HTTP call
8. **DI swap** — register `AnthropicAiProvider` for the Anthropic kind (replacing the stub); keep the stub only if still useful for tests. Wire key-store + endpoints
9. **Live smoke** — owner configures a real key; verify `/generate` returns Claude drafts; confirm no key in logs

## Notes
- **Security is the point of this iteration, not an afterthought.** Keys are encrypted with `IDataProtectionProvider`, decrypted only at request time, never logged, never serialized back. A test must assert the list endpoint returns provider *kinds*, not key strings. Treat a leaked key as a failed DoD.
- **Anthropic only is intentional.** Building OpenAI/Gemini/OpenRouter clients we cannot run live yet would be untested code (ADR-019). They get their own iterations once keys exist; the enum carries them now so the resolver's "unknown kind" path is real.
- The provider must degrade gracefully when the user has no key for the requested kind — a typed `MissingAiKeyException` mapped to a 4xx, not an unhandled 500.
- Rate limiting (ADR-006 consequence) is **out of scope here** — note it for a later iteration; this one establishes storage + one provider.
