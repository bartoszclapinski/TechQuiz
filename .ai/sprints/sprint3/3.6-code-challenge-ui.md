# Iteration 3.6 — Code challenge UI (Monaco editor + run/grade verdict)

> Phase 3 · Status: planned

## Goal
Make the execution-backed coding tasks (ADR-018) usable from the browser. The backend vertical
already exists on `master` — list challenges, compile + run in Judge0, and grade against hidden
test cases with a **compile gate** (compile first, evaluate success only when it compiles). This
iteration adds the frontend: a challenge list, a focused editor screen (Monaco) where the user
writes C#, runs their code, and submits for grading, and a verdict view that shows
**compile failure** distinctly from **test pass/fail**.

No backend behavior changes are planned — this is a frontend slice over the existing API.

## Scope (decided with owner)
- **In:**
  - `features/code-challenges/` — api client + hooks (list = query, grade = mutation, run = mutation).
  - **Challenge list view** — cards with title, difficulty badge, prompt preview; route + nav entry.
  - **Challenge editor screen** — Monaco editor seeded with `starterCode`; "Run" (custom stdin via
    `POST /api/code/run`) and "Submit" (grade via `POST /api/code-challenges/{id}/grade`).
  - **Verdict UI** — two-stage, mirroring the backend: when `Compiled === false`, show the compiler
    output prominently and **no** test rows; when compiled, show per-case pass/fail
    (`PassedCount/TotalCount`) using each case's `Status` + the user's own `ActualStdout`/`Stderr`.
  - Monaco Editor dependency (`@monaco-editor/react`) — see "New dependency" below.
  - Both themes; editor uses a dark surface in light mode (consistent with ADR-016 code blocks).
- **Deferred:**
  - **Persistence / authoring** of challenges — `InMemoryCodeChallengeCatalog` stays the source.
  - The non-executing variants **CodeOutput / CodeFix / FillIn** (option/answer-graded) — separate work.
  - **AI qualitative feedback** on submissions — iteration 3.7 (ADR-018 reframes AI as complementary).
  - Saving attempts / scoring history for code challenges.

## Key constraint — the hidden harness never leaks
`CodeChallengeDto` already omits test cases, and `CodeChallengeCaseResult` exposes only the user's
**own** `ActualStdout`/`Stderr` plus a per-case `Passed` + `Status` — never the case `Stdin` or
`ExpectedStdout`. The verdict UI must surface only what the API returns; it must not try to display
or reconstruct expected outputs (mirrors hard rule #4 for quizzes).

## Contract (consumed, unchanged)
- `GET /api/code-challenges` → `CodeChallengeDto[]` `{ id, title, difficulty (name), prompt, starterCode }`.
- `POST /api/code/run` `{ sourceCode, stdin? }` → `CodeExecutionResult`
  `{ status, stdout, stderr, compileOutput, timeSeconds, memoryKb }` — powers "Run" against custom input.
- `POST /api/code-challenges/{id}/grade` `{ sourceCode }` → `CodeChallengeGradeResult`
  `{ compiled, compileOutput, passed, passedCount, totalCount, cases[] }`, where each case is
  `{ orderIndex, passed, status, actualStdout, stderr, compileOutput }`.
- Difficulty stays an enum **name** on the wire, consistent with the rest of the app.

## New dependency
- **`@monaco-editor/react`** — the standard React wrapper around the Monaco editor (VS Code's editor
  core), already anticipated for Phase 3 in the stack table (CLAUDE.md) and ADR-018's editor mention.
  Justification per hard rule #6: a real code editor (syntax highlighting, C# tokens, sane keybindings)
  is core to the differentiator; hand-rolling over a `<textarea>` is strictly worse and Monaco is the
  de-facto choice. Loaded only on the challenge route so it doesn't bloat the main bundle.
