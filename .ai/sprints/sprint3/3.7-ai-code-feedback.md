# Iteration 3.7 — AI feedback on code submissions

> Phase 3 · Status: done

## Goal
Add **qualitative AI feedback** on a code-challenge submission, complementing the deterministic
test verdict from 3.6. After grading (or independently), the user can ask an AI provider — using
their own key (BYOK, ADR-006) — for prose feedback on their C#: what's good, what's risky, what edge
cases they missed, how to improve. The deterministic test harness stays the **grader**; AI is
explicitly *complementary*, never the pass/fail authority (ADR-018).

This is the last iteration of sprint 3.

## Scope (decided with owner)
- **In:**
  - Extend the `IAiProvider` port with a **code-feedback** method (additive to the existing
    `GenerateQuestionsAsync`); implement for **Anthropic** (the only key verifiable end-to-end today).
  - Application use-case (TDD): `GetCodeFeedbackCommand` — resolve provider, load the caller's key,
    call the provider with the prompt + submission + grade summary, return the feedback text.
  - API endpoint: `POST /api/code-challenges/{id}/feedback`.
  - Frontend: an **on-demand** "Get AI feedback" control on the code-challenge editor screen
    (a mutation, with loading + error states); render the returned prose.
- **Deferred:**
  - AI feedback for the **non-executing** variants (CodeOutput/CodeFix/FillIn) — those variants
    aren't built yet.
  - Feedback for option-based quiz questions (the quiz Result screen) — out of scope here.
  - Persisting/caching feedback, streaming tokens, multi-provider feedback beyond Anthropic.

## Where feedback lives (reconciling the README)
Sprint-3 README placed 3.7 feedback "in the Result screen". Code challenges (ADR-018) don't use the
quiz Result screen — they have the **editor screen** (3.6) with a verdict panel. Feedback therefore
lands on the **code-challenge editor screen**, next to the test verdict, triggered on demand. The
README line is reframed accordingly (one-line note, like the 3.6 reframing).

## Key constraint — feedback must not leak the hidden harness
The provider runs server-side, so it *may* receive the hidden test data to reason about failures, but
the **prompt must instruct the model to give guidance without quoting exact expected outputs**, and
the returned text is treated as untrusted prose for display. The point of feedback is "you don't
handle empty input", not "test 2 expects `30`". This preserves the spirit of hard rule #4 for the
code-challenge harness.

## Contract (new in 3.7)
- `POST /api/code-challenges/{id}/feedback` — body `{ sourceCode, provider }` (provider as enum
  **name**, consistent with the rest of the AI feature). Returns `{ feedback: string, provider:
  string }`. `401` unauthenticated, `404` unknown challenge, `409` `MissingAiKeyException` (no key for
  that provider — same mapping as generate).
- Feedback is plain text/markdown prose; no structured score (the score is the test verdict).
