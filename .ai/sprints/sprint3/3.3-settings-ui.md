# Iteration 3.3 — Settings UI: managing AI provider keys

> Phase 3 · Status: planned

## Goal
Give the user a real, navigable Settings page where they can configure the bring-your-own-key
providers — add/rotate a key, see which providers are configured, and remove a key — entirely
over the existing `/api/ai/keys` contract built in 3.2. The frontend is a thin client over that
contract: it sends a key once over HTTPS and otherwise only ever displays *which* providers are
configured, never the key material itself (the API never returns it — ADR-006).

This iteration is **UI only**. The encrypted storage, per-user isolation, and "never log / never
return the key" guarantees already exist and are verified (3.2). Nothing here touches the backend.

## Scope (decided with owner)
- **In:** key management UI — set/rotate, list-configured, remove — for the four `AiProviderKind`
  values, with only **Anthropic** actually configurable now (the only provider with a live client).
  OpenAI / Gemini / OpenRouter render as **"soon"** (disabled), consistent with the topbar's
  `COMING_SOON` pattern (ADR-014: show what's coming, don't let users store a key they can't use).
- **Deferred to 3.4:** selecting an *active* provider for generation (the Generate screen owns that).
- **Deferred (no backend):** usage stats / quota display — there is no usage-tracking endpoint yet.

## Definition of Done
- [ ] A `Settings` route (`/settings`) behind `RequireAuth` + `AppShell`, reachable from a real
      topbar nav link (promote "Settings" out of the disabled `COMING_SOON` set, or add it fresh)
- [ ] Settings feature folder (`web/src/features/settings/`) following the existing feature-folder
      convention: `api.ts`, `query-keys.ts`, `use-*.ts` hooks, `settings-page.tsx`
- [ ] Lists all four providers; each row shows configured state ("Configured" vs "Not configured")
      from `GET /api/ai/keys`. Anthropic is interactive; the other three are visibly "soon"/disabled
- [ ] Add/rotate: a masked input (`type="password"`) + Save → `PUT /api/ai/keys {provider, apiKey}`.
      On 204, the list refetches (TanStack Query invalidation) and the input clears. The key is never
      echoed back, stored in component state longer than needed, or persisted client-side
- [ ] Remove: a Remove action on a configured provider → `DELETE /api/ai/keys/{provider}`, with a
      confirmation step, then list refetch
- [ ] Validation feedback surfaced to the user: empty key and API 400 (unknown provider / empty key)
      show an inline error, not a silent failure or a thrown toast only
- [ ] Loading / error / empty states handled (mirror `categories-page.tsx`: loading text, error +
      Retry). Pending mutations disable the relevant controls (`aria-busy`)
- [ ] Verified manually in the browser in **both dark and light themes** using existing design tokens
      (`bg-surface`, `border-default`, `text-secondary`, `bg-accent-bg`, etc.) — no hardcoded colors
- [ ] `pnpm build` (or `tsc`) clean: TS strict, no `any`, named module-level functions

## Tasks (in order)
1. **Feature scaffold** — create `web/src/features/settings/` with `query-keys.ts`
   (`aiKeysKey()`), and `api.ts` exposing the `/api/ai/keys` contract:
   `fetchConfiguredProviders(): Promise<string[]>`, `setAiKey(provider, apiKey): Promise<void>`,
   `removeAiKey(provider): Promise<void>`. Mirror `features/categories/api.ts` style.
2. **A provider catalog constant** — the four `AiProviderKind` names + display label + `available`
   flag (only Anthropic true now). Single source for rendering the list. Keep it in the feature.
3. **Query + mutation hooks** — `useConfiguredProviders()` (`useQuery`), `useSetAiKey()` and
   `useRemoveAiKey()` (`useMutation`, both invalidate `aiKeysKey()` on success). Mirror
   `use-categories.ts` / the quiz mutation hooks.
4. **`settings-page.tsx`** — render the catalog; per provider show configured pill + actions.
   Anthropic row: masked input + Save + (when configured) Remove with confirm. Disabled rows for
   the "soon" providers. Wire loading/error/empty + inline validation. Match the categories-page
   layout shell (`<main className="mx-auto max-w-...">`, heading block).
5. **Routing + nav** — add `<Route path="/settings" element={<SettingsPage />} />` inside the
   `RequireAuth`/`AppShell` group in `App.tsx`; add a working "Settings" `NavLink` to the topbar
   (remove it from `COMING_SOON` if present — it is not currently listed, so add fresh).
6. **Manual verification** — run `pnpm dev`, log in as the demo user, round-trip a key
   (add → see "Configured" → remove → see "Not configured"), confirm the empty-key and
   bogus-key paths show inline errors, and check both themes. Note the result in `LOG.md`.

## Notes
- **Security is already handled by the backend.** This UI must not regress it: never display the key
  after entry, never write it to `localStorage`/query cache, and rely on the API's HTTPS `PUT` as the
  only place the key crosses the wire. The list endpoint returns provider *names* only — render those.
- **No new dependency.** Axios + TanStack Query + react-hook-form/zod (already in the stack) cover
  this. A masked `<input>` + a one-field form is enough; don't pull in a form library page-section if
  the existing inline pattern suffices (soft pref #5 — fewer, larger components).
- **Owner is learning React** — favor the established hook/feature patterns already in `web/` and
  explain non-obvious choices (query invalidation, why the key never lands in component state) inline
  in the PR / conversation, not in code comments.
- **`COMING_SOON` topbar:** promoting "Settings" to a live link is the first real nav item beyond
  Categories. Leave Generate/Dashboard/History/Daily review disabled — their iterations come later.
