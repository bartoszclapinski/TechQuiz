# Iteration 5.1 — Native OpenAI provider

> Phase 5 · Status: in-progress

## Goal
A user with their own OpenAI key can generate questions and get code feedback through a native `OpenAiAiProvider` on the existing `IAiProvider` seam, with the same behaviour, tests and error handling as Anthropic (ADR-019).

## Definition of Done
- [x] `OpenAiAiProvider` (Infrastructure, `internal sealed`, typed `HttpClient`, no SDK) implements both `IAiProvider` methods for `AiProviderKind.OpenAi`. The key goes in `Authorization: Bearer` per `HttpRequestMessage`, never in `HttpClient` defaults; every request sends `store: false` (#393)
- [x] `OpenAiOptions` binds `Ai:OpenAi` (`BaseUrl` = `https://api.openai.com/`, `Model`, `MaxCompletionTokens`, `ReasoningEffort` = `low`), validated on start. No model id in Application or `web/` (#393)
- [x] Prompts, the `{ "questions": [...] }` contract and fence-stripping live in one shared helper used by both providers (`AiPrompts`, #389, #390)
- [x] Both providers throw Application-level `AiProviderRejectedException` (`InvalidKey` | `QuotaOrRateLimit`), mapped to 422 / 429 — never 401, which `api-client.ts:65` treats as an expired session (#391; OpenAI in #393)
- [x] Both typed clients are registered by name; a DI test on the real `AddInfrastructure` resolves both kinds and each request goes to its own host (`api.anthropic.com` / `api.openai.com`) — `AiProviderWiringTests` (#392, #393)
- [x] ≥ 14 `OpenAiAiProviderTests` (fake handler): the 11 Anthropic tests adapted (Bearer, `v1/chat/completions`, `store: false`, strict `json_schema`; 401 → `InvalidKey` for both methods) + 429 → `QuotaOrRateLimit`, `message.refusal` / `finish_reason: "length"` / null content → `AiResponseException` — 18 tests (#393)
- [x] 422 / 429 messages on Generate and code feedback; providers shown by label; a provider `<select>` for code feedback when more than one key qualifies. `OpenAi` stays `available: false` ("soon") in `web/src/features/settings/api.ts` until the live run (see Decisions 6) (#394, #395)
- [x] No key material in logs, DTOs or responses: rejection messages are fixed text, never the upstream body — a test sends a key-shaped string to a 401 stub and asserts neither the message nor ProblemDetails `detail` contains it (provider tests for both + Api 422 test; log check pending task 9)
- [ ] **Live smoke (partial):** the bogus-key path is verified against the real OpenAI API (401 → 422) and Anthropic generation is re-checked on the new `{ "questions": [...] }` contract. The funded-key run and the flag flip are a follow-up (Decisions 6, ADR-019)

## Notes
- **No new dependency.** Raw `HttpClient`, as in 3.2. The `OpenAI` NuGet package was rejected: the per-call BYOK key doesn't fit its per-client credential model without extra wiring, and two providers would use two HTTP styles. No shared OpenAI-compatible base class is built ahead of 5.3.
- **Named clients are a fix, not style.** Two unnamed `AddHttpClient<IAiProvider, …>` calls don't throw; they share one name and the last `BaseAddress` wins, so Anthropic would POST to OpenAI.
- **Out of scope:** key test on save, org/project headers, retries, Anthropic 529 mapping, a 502 for `AiResponseException`, rate limiting (ADR-006), persisting the Data Protection key ring on Render. No migration (the enum is stored as a string). `README.md:45`/`:71` already name OpenAI.

## Decisions (agreed with the owner, 2026-11-08)
0. **Phase 5**, recorded in ADR-027 amending ADR-013 — not an iteration 3.8 in a closed phase.
1. **`v1/chat/completions`**, not the Responses API. OpenAI now recommends Responses, but Chat Completions stays supported, needs no tools here, and is the shape OpenRouter speaks (5.3).
2. **Strict `json_schema`.** It needs an object root, so both providers move to `{ "questions": [...] }` (task 3); Anthropic generation is re-checked at the smoke.
3. **`gpt-6-luna`** (OpenAI's fastest, most cost-effective GPT-6 model), `ReasoningEffort = low` (reasoning tokens count against `max_completion_tokens`). Overridable via `Ai__OpenAi__Model`.
4. **Typed failures for Anthropic too** — otherwise the same bad key is a 422 from one provider and a 500 from the other.
5. **Code feedback gets a provider `<select>`** when more than one key qualifies (today `code-challenge-page.tsx:62-64` takes the first match, so Anthropic always wins).
6. **No funded OpenAI key yet.** 5.1 merges with OpenAI still "soon"; the funded-key run and the `available: true` flip ship as a small follow-up PR under the issue opened in task 9.
